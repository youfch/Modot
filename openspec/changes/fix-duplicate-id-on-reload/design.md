# Design

## D1 修在查重处，不在 `loadedMods.Add` 处兜底

两种改法都能消掉异常，但只有一种是对的：

- **A（采用）**：让 `LoadModMetadata` 的查重也看 `ModLoader.LoadedMods`，于是跨调用重复走既有的"记录 + 跳过"路径
- **B（不采用）**：在 `loadedMods.Add` 外包一层 `try/catch(ArgumentException)`

B 的毛病有两个：一是**靠异常做流程控制**（重复 ID 是可预期的输入，不是异常情况）；二是它在**已经走完全部加载流程之后**才兜底 —— mod 已经构造、程序集已经载入、补丁已经枚举，然后才发现 ID 撞了，白做且可能留下副作用。A 在最早的阶段就把重复挡掉。

## D2 不改"第二次加载应该发生什么"这个语义

那是产品决策（返回空？重载？拒绝？）。本变更只统一**失败/报告方式**：既有契约（调用内重复）已经是"记录并跳过"，跨调用没有理由不同。结果层面也不变 —— 此前第二次加载同样是"不加载"，只是以未处理异常的形式结束。

## D3 断言要被故意打红

`reload` 场景当前断言的是**实测**的 `ArgumentException`，注释里写明"修复时会打红"。本变更必须同步改该断言 —— 那正是它存在的意义，而不是顺带清理。

## D4 为什么需要一个"断言日志"的机制

修好之后，第二次加载的表现是"**不抛异常、返回 0 个**"，而"为什么是 0 个"（`Duplicate ID`）只体现在**日志**里。只断言"0 个"会漏掉"因为别的原因没加载"这类回归。

所以给 runner 的场景表加 `ExpectOutput`：声明后，该场景的**宿主输出必须包含**指定文本，否则判失败。这是对既有 `ExpectFailure`（断言退出码）的互补 —— 一个断言"失败得对不对"，一个断言"说清楚了没有"。首个使用者是 `reload`（`ExpectOutput = 'Duplicate ID'`）。

## D5 验证方式

`reload` 场景 + 全套件。需特别确认 `single-load`（走 `LoadMod`，不经过 `LoadModMetadata`）不受影响，以及 `duplicate` / `incompatible`（调用内路径）行为不变。
